## Per-file browser persistence journal (2026-09-21)

Production filesystem.js now installs persistence-journal.js before mounting IDBFS. The adapter wraps IDBFS-backed MEMFS node/stream operations and journals successful local creates, writes, attribute changes, removals and rename descendants. Restore operations suppress journal recording. Each mount serializes sync requests; outgoing sync snapshots only journaled entries (copying file bytes) and commits them in one IndexedDB transaction. An unchanged runtime has no outgoing entries and therefore cannot erase or overwrite another runtime's changes.

Journal records carry versions. A successful transaction clears only the versions it captured, retaining writes made while it was pending; failed/aborted transactions retain all pending changes. Missing parent directories are created when needed. A stale rmdir preserves a directory if remotely added children would otherwise be orphaned. Actual conflicting edits to the same file use transaction commit order; this is not a semantic merge of save files. Unsupported IDBFS node types still fail rather than silently claiming persistence.

### 2026-09-22 — the browser and native builds were drawing different random numbers

The simulation seeds one `std::mt19937` with a constant on purpose, so a run is reproducible. Every random decision in the game comes from that stream: terrain debris placement and sprite choice, weapon spread, gib velocities, AI and scripted randomness. `std::mt19937` is specified exactly; `std::uniform_int_distribution` and `std::uniform_real_distribution` are not, and libstdc++ (native, GCC 13) and libc++ (Emscripten) map the same engine output onto a range differently. The constant seed therefore bought nothing across platforms, and the two builds diverged from the first scene load.

Demonstrated with the same seed and the same expressions — native `int[0,1000]`: 699 565 797 181 264 …; browser: 877 457 400 306 156 …

Fix: `RandomGenerator` moved from `RTETools.h` into a dependency-free `RandomGenerator.h`, with the standard distributions replaced by an explicit mapping — unbiased rejection sampling for integers (discarding the `2^32 mod range` lowest draws, with a 64-bit variant for wide spans) and a 24-bit fixed-point unit interval. `tests/random_contract.cpp` prints the engine's sequence; compiled for Wasm (`--target random_contract`) and natively with g++-13 it now produces byte-identical output. Uniformity checked over three million draws (three-way range 0.3339/0.3334/0.3327; fifteen-way range within 0.06645-0.06691 of 0.06667).

Both games rebuilt clean and the browser game verified live: Tutorial Mission loads and renders correctly, with debris now placed by the new shared sequence. Consequence to remember: both builds now differ from the shipped `*.preview.png` images, which came from a libstdc++-distribution build, so preview comparisons cannot reach 100% and the native game must be rebuilt before comparing it with the browser build.

Checked the same class of silent drift in arithmetic with a new `float_contract` target. Multiply-add, `cosf`, `sqrtf`, `powf`, `expf`, `logf`, `fmodf`, vector normalize, rotate and double-precision `sin` are bit identical between the native and Wasm builds; the native build does not contract multiply-add into an FMA that Wasm cannot express. `sinf` and `atan2f` differ by one unit in the last place on one sample each, because Emscripten ships a musl-derived libm. Left alone deliberately, with reasoning in notes/randomness.md: the engine already advances a variable number of simulation steps per drawn frame, so trajectory determinism is not a property it has, and one-ULP libm differences sit below that noise. The random stream was different in kind because it changed which sprite, position and rotation were picked, visibly, from the first scene load.

### 2026-09-22 — audio mixes on its own thread; the worklet was never the problem

Audio now runs on an AudioWorklet thread. The previous two attempts at this were reverted with the note "links and runs, device started, node connected, output exactly zero, no error", and that conclusion was right about the symptom and wrong about the cause.

Four measurements separated the possibilities. A new `worklet_probe` target drives a raw `ma_device` with a sine under the engine's exact flag combination — worklet, Wasm Workers, Asyncify, `-pthread`, memory growth — and reaches the destination at peak 0.25, 375 callbacks a second; growing the heap 256 MB mid-playback changes nothing. The same probe through `ma_engine`'s node graph: also 0.25. `audio_check` decoding the real `PistolFire.flac` through `ma_engine`: peak 1.10. And the game itself: engine clock advancing at exactly 48 kHz, one channel playing, unpaused, unmuted, every volume 1.0, and mixer output exactly zero.

That last measurement needed the engine to report its own mixer, which it now does — `ma_engine_config.onProcess` samples the output peak on the audio thread, and `?perf-debug` prints it with the device state, active channels, the peaks either side of the per-channel fader, and each channel's playback cursor. The cursor was frozen at 1115 frames while the fader ran 3800 times per two seconds: the graph was running and the data source was producing nothing.

`CountedSource` wrapped a `ma_decoder` built with `ma_decoder_init_file`, so every read reached the filesystem on whichever thread pulled the graph. In the browser that filesystem is Emscripten's JavaScript glue, and it does not exist on an AudioWorklet thread — a Wasm Worker has no such environment, and the reads returned nothing silently. The ScriptProcessorNode path worked precisely because its callback ran on the main thread. `audio_check` worked for the mirror-image reason: `ma_engine_play_sound` decodes the whole file up front, so its audio thread only touches RAM.

Fix: `System::playSound` reads the file on the calling thread and uses `ma_decoder_init_memory`, so the audio thread makes no host call at all. The bytes live in a `shared_ptr` on `CountedSource`, declared after the decoder so it outlives it, with a `weak_ptr` cache on `SoundState` — concurrent plays share one copy and it is freed with the last channel. Decoding, looping and tail handling are unchanged. Memory is bounded by what is audible rather than by the 288 MB of audio in `Data`.

### 2026-09-22 — the simulation itself matches, and the original engine did not reproduce itself

Scene generation being identical says nothing about what happens once objects move. `-simulate-tutorial <steps>` (browser `?simulate=<steps>`) starts the real Tutorial mission, runs a fixed number of simulation steps with a fixed time step and no input or rendering, and prints the object count, a hash of every object's identity, position, velocity, rotation and mass in MOID order, and the random stream. It writes the terrain afterwards too, so weapon damage is comparable.

The first run of it found something more basic than a porting difference: three native runs of the same 600 steps gave **86, 87 and 83 objects** with three different hashes. Scripts and actor sight run on a thread pool, objects created by scripts take their identity from an atomic counter, and MOID assignment was a queued background task, so the result depended on how the threads interleaved. The original engine is not reproducible against itself.

Behind `System::IsInDeterministicSimulationMode()`, so ordinary play is untouched: the two threaded script loops in `MovableMan` run one state at a time in order; `CastSeeRays`, `UpdateDrawMOIDs` and the Lua garbage collection step run inline; `ParallelAlgorithms::ForEach` takes its serial path in both builds.

Two ordering defects had to be fixed outright, because they affect ordinary play as well:

- `LuaStateWrapper` kept its objects in `std::unordered_set<MovableObject*>` and ran their scripts in that container's iteration order — an order that depends on the allocator and the standard library's bucket policy, so libstdc++ and libc++ ran the same scripts in different orders. It is now a `std::set` ordered by `GetUniqueID()`, a monotonic counter that is the same in both builds.
- The number of Lua states was `std::thread::hardware_concurrency()` natively and the worker pool size in the browser (12 against 4 here). Objects are handed to states round robin as they are created, so the count decides which state runs an object's scripts and therefore which random stream it draws from. It is a fixed 8 in both now, with `NumberOfLuaStatesOverride` still able to change it.

With those, four consecutive native runs give one hash, and the browser gives the same one:

| steps | objects | state hash | random draws |
| --- | --- | --- | --- |
| 600 | 83 | `23382cdb0676be73` | 18930, `e26df854fb7f6d90` |
| 1800 | 83 | `17b3b9f6c4182b03` | 42435, `d8b18b29fb1c1a15` |
| 3600 | 84 | `b23892cfa75d3748` | 73642, `60add2735f3f51da` |

3600 steps is a minute of play at 60 Hz with actors, AI, weapons fire, physics, collisions and Lua running. The terrain left behind, damage included, is byte identical at full resolution on both. Scene previews and full terrain dumps were re-verified after these changes and remain byte identical, with matching stream hashes.

This establishes that the two builds compute the same simulation from the same inputs. It does not make ordinary play bit-reproducible, and nothing could: normal play keeps the thread pool, and the original is already non-reproducible against itself for that reason.


### 2026-09-22 — threaded play is deterministic too; it was a data race, not a property of threads

The previous entry concluded that ordinary threaded play could not be bit-reproducible and that the original engine was inherently non-reproducible. That was wrong. Threading does not imply nondeterminism; one defect did.

`-simulate-tutorial <steps> [mask]` now takes a bitmask of which parallel phases stay parallel, which turns the question into a bisection. Running each phase parallel on its own, three times each: threaded object scripts, actor sight rays, the MOID task, `ParallelAlgorithms::ForEach` and the async Lua garbage collection all reproduced exactly. Only the threaded AI script phase varied — and the giveaway was that the *number* of random draws changed between runs (18930, 18927, 19238, 18784), not just their order.

`g_RandomGenerator` is one `std::mt19937` with nothing guarding it, and every `RandomNum` call in C++ went to it. Scripts run on several threads at once, so everything they reach — weapon spread, gib velocities, scattering — was drawing from one generator concurrently. A data race on the engine's most order-sensitive state.

Fix: each script state gets its own simulation stream. `LuaStateWrapper` gains `m_SimulationRandom`, seeded from the same dedicated generator as its Lua one, and `LuaMan::SetThreadLuaStateOverride` points a `thread_local RandomGenerator*` at it. `SimulationRandom()` in `RandomGenerator.h` returns that when set and the global generator otherwise, so a thread running on behalf of a state can never share a generator. No call site changed. Alongside it, objects created during a parallel phase are appended to `m_AddedActors`/`m_AddedItems`/`m_AddedParticles` under mutexes in whatever order the threads took the locks, and that became the order of the simulation's own lists; they are sorted by unique ID before the merge now.

Result: threaded and serial produce the same simulation, and so do the two builds. Six native runs fully parallel, three browser runs, and the fully serial run all agree.

| steps | threading | objects | state hash | random draws |
| --- | --- | --- | --- | --- |
| 600 | fully serial | 84 | `9bf55a463602322b` | 20303, `c09fb36567284fcd` |
| 600 | fully parallel | 84 | `9bf55a463602322b` | 20303, `c09fb36567284fcd` |
| 3600 | fully parallel | 79 | `28440154e5496db4` | 69409, `2862ee98b4cc8c80` |

The browser pool is four threads and this machine has twelve cores. The terrain after 3600 threaded steps, weapon damage included, is byte identical at 2110x840. Live play after the change: 60 FPS, 58 UPS, frame 16.7 ms, 9188 objects, audio continuous with no late callbacks.

A measurement trap worth recording: `GetMOIDCount` reads an index a pool thread rebuilds, so the harness drains both pools before hashing. Without that it reported 84, 38 and 4 objects for identical simulations.

### 2026-09-24 — mission frame time 15.2 → 4.6 ms; faster loading

Measured on headless Chrome's Metal backend, Dummy Assault at 1920×1080, scale 2.

**The engine was waiting, not working.** The frame report said 15 ms of engine time per frame, but a V8 CPU profile (`cc.sh profile`, new) showed the main thread idle for three quarters of it, and a trace showed about eight `setTimeout` tasks per frame, the later ones 4 ms apart. They came from `BS::multi_future::wait`, which on the main thread yielded with `emscripten_sleep(0)` on every poll while the pool ran the script and AI states. Chrome clamps nested timers to 4 ms. The wait now spins with `wait_for(1 ms)` — a futex wait that services calls workers proxy to the main thread — and only yields through `BrowserCooperativeYield` after about a frame; `ParallelAlgorithms::ForEach` waits the same way. Simulation update on the overlay: 12.3 → 2.6 ms.

**Cooperative yields** are throttled from the last event loop turn, and the per-frame wait now counts as one (`BrowserNoteEventLoopTurn`), so they never fire during ordinary play; the `?perf-debug` frame report counts mid-frame yields. They resume from a `MessageChannel` message instead of a timer: `emscripten_sleep(0)` hit the same 4 ms clamp on every load yield, and `scheduler.yield()` starved page timers for an entire load. Title screen after Play: 7.9 → about 6 s. New yield points remove the startup blocks: between managers in `main`, between Lua states, per row of `FrameMan`'s 21 transparency tables (via `create_trans_table`'s progress callback), per GUI control built from a layout file. No block over 250 ms remains.

**Synchronous GL queries.** `glGetError` once per frame cost ~0.6 ms (a round trip to the GPU process); it now runs every 120 frames (errors stay latched). `BigTexture::Update` queried six pixel-store values per upload to restore them; it now sets the packed layout unconditionally and leaves it with nothing bound, as the original's `Update` does. `texture_gpu_contract` updated to that contract and passes.

**Checks.** New `thread_wait` target (the old test source was not built by anything): twenty short waits must not reach the event loop by any route (the old wait: 95 ms and fails; now 2 ms), a long wait lets page timers run, worker stdout is serviced during a wait in ~1 ms. `gui_input_contract` passes.
